# Deploy Qwesie TV for free (Render + Neon)

This guide puts Qwesie TV online at a public HTTPS URL so scorers, viewers and OBS
can use it from anywhere. It uses **Render's free web service** (Docker, WebSockets,
no credit card) and a **free Neon Postgres** database (does not expire).

> **Why not Vercel?** Qwesie TV is a long-running Express + Socket.IO server with
> in-memory broadcast state and a background scheduler. Vercel Functions are
> request-scoped (WebSocket connections are capped at 300s on Hobby, and separate
> instances do not share Socket.IO rooms), so the live scoring/broadcast features
> would not work reliably. Render runs the whole app as one container, which is what
> this app needs.

## 1. Create the free database (Neon)

1. Go to <https://neon.tech> and sign up (GitHub login is fastest).
2. Create a project, for example `qwesie-tv`.
3. Open **Connection Details** and copy the **direct** connection string. It looks like:
   ```
   postgresql://user:password@ep-xxxx-xxxx.aws.neon.tech/neondb?sslmode=require
   ```
4. Keep this string; Render asks for it in step 3.

Neon's free plan is enough for a scoreboard: 0.5 GB storage and automatic suspend
when idle (the first request after a long idle period may take a few seconds).

## 2. Deploy the Blueprint

Open this link (the repository is public):

<https://render.com/deploy?repo=https://github.com/Vinc3980/Qwesie_Scoreboard>

Or manually: Render Dashboard -> **New** -> **Blueprint** -> connect GitHub ->
select `Vinc3980/Qwesie_Scoreboard`.

The `render.yaml` in the repo creates:

| Setting | Value |
|---|---|
| Service type | Web Service (Docker) |
| Plan | **free** |
| Health check | `/api/v1/health` |
| `NODE_ENV` | `production` |
| `SERVE_CLIENT` | `true` (API + UI + Socket.IO on one origin) |
| `JWT_SECRET` | generated by Render |
| `DATABASE_URL` | **you paste the Neon pooled string** |
| `DATABASE_URL_UNPOOLED` | **you paste the Neon direct string** (used by migrations) |

> Render's own free Postgres also works for a trial, but it **expires after 30 days**.
> Prefer Neon so match history is not lost.

## 3. Apply and wait for the first deploy

1. In Neon, open your project -> **Connect** and copy **both** connection strings:
   - the **pooled** one (host contains `-pooler`) for `DATABASE_URL`;
   - the **direct** one (host has no `-pooler`) for `DATABASE_URL_UNPOOLED`.
2. When Render prompts, paste each value into its matching variable.
3. Click **Apply** / **Create**. The first Docker build takes a few minutes.
4. The container automatically runs `prisma migrate deploy` on startup (using
   `DATABASE_URL_UNPOOLED`). It retries 5 times, then exits instead of serving a
   stale schema.
5. When the health check passes, open the service URL, e.g.
   `https://qwesie-tv.onrender.com`.

### If the database is brand new

The repo's migration history was imported from an existing schema, so it does
**not** build a database from empty (the first data-contract migration expects
tables that no earlier migration creates). The current Neon database has already
been baselined once. For a **new empty** database, baseline it first from the
repo root, then start the service:

```bash
# DATABASE_URL / DATABASE_URL_UNPOOLED set to the new Neon branch
npm exec --workspace=server -- prisma db push --force-reset --skip-generate
for m in server/prisma/migrations/*/; do
  npm exec --workspace=server -- prisma migrate resolve --applied "$(basename "$m")"
done
npm exec --workspace=server -- prisma migrate status
```

After that, normal `prisma migrate deploy` (which the container runs) applies
only newly added migrations.

> PowerShell equivalent for the loop:
> `Get-ChildItem server/prisma/migrations -Directory | ForEach-Object { npm exec --workspace=server -- prisma migrate resolve --applied $_.Name }`

## 4. Create the first admin

On a fresh database the app shows the bootstrap/setup screen. Create the admin
account there, then sign in. Create SCORER and VIEWER accounts from the users page.

If the setup token is required, it is printed in the Render logs on first boot
(look for `BOOTSTRAP_SETUP_TOKEN` / setup-token output), or set
`BOOTSTRAP_SETUP_TOKEN` yourself in Render -> Environment.

## 5. Output links (OBS)

The Outputs panel builds links from the browser's current origin, so they update
automatically to the new public URL:

```
https://qwesie-tv.onrender.com/out/court/1/scorebug
https://qwesie-tv.onrender.com/out/court/1/graphics
https://qwesie-tv.onrender.com/out/court/1/all
```

Paste those into OBS browser sources (1920x1080). On a public host the panel no
longer appends `:5000` or the container's private LAN IP.

If you add a custom domain in Render, the links switch to that domain automatically.

## 6. Free-tier behaviour (read this before match day)

- **Cold start:** a free service sleeps after 15 minutes without traffic and takes
  about a minute to wake. Open the console once before the match, and keep at least
  one output/console connected while live.
- **Restarts:** Render may restart free instances at any time. Socket.IO clients
  reconnect and resync automatically, but expect a brief interruption.
- **Uploads are ephemeral:** team logos and player photos saved to local disk are
  lost when the instance restarts or redeploys. Match data in Postgres is safe.
  For permanent branding, upload logos again after a deploy, or add external object
  storage (Cloudinary/S3/Supabase Storage) later.
- **Backups:** free instances have no `pg_dump` and no persistent disk, so the
  in-app backup scheduler is disabled (`BACKUP_ON_START=false`). Use Neon's own
  backup/branching features.
- **One instance only:** free plan = 512 MB RAM / 0.1 CPU. Do not enable autoscaling;
  Socket.IO broadcast state is in memory and requires a single instance.

For a real event where downtime is unacceptable, upgrade the Render web service to
the `0.5c-512mb` ($7/month) plan; it never sleeps and adds a persistent disk option.

## 7. Deploying updates

Every push to `main` triggers a new Render deploy:

```bash
git add .
git commit -m "your change"
git push origin main
```

Migrations run automatically on container start. Keep migrations backwards
compatible when possible.

## 8. Troubleshooting

| Symptom | Check |
|---|---|
| Build fails at `npm ci` | `package-lock.json` must be committed and in sync with `package.json`. |
| `prisma migrate deploy` fails | `DATABASE_URL_UNPOOLED` (or `DATABASE_URL`) must be reachable from the internet and include `sslmode=require` for Neon. The direct Neon host has no `-pooler`. |
| 502 / loading page for ~1 min | Free instance is waking up. Open the URL again. |
| Login cookie not sticking | Access the app over the `https://` Render URL, not the internal port. |
| Output shows old `:5000` link | Hard-refresh the console (Ctrl+F5) so the new client build loads. |
| Output connects but no score updates | Keep one console tab open; check Render logs and `/api/v1/health`. |
